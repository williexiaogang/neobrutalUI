# ADR-001: 采用独立组件库实现方案，不复用 daisyUI 类名

- 日期：2025-01-15
- 状态：accepted

---

## 背景（Context）

daisyUI 是目前最流行的 Tailwind CSS 组件库之一，其组件分类方式、API 设计思想（如通过 `class="btn btn-primary"` 快速组合语义化组件）和主题系统设计得非常优秀。然而，本项目的目标是打造一个具有**独立视觉身份**的新粗野风格（Neo-Brutalism）UI 组件库。新粗野风格拥有独特的视觉语言——高对比度边框、硬阴影偏移、鲜艳色块、几何化排版——这些视觉特征与 daisyUI 的默认风格差异巨大。

如果复用 daisyUI 的原始类名（如 `btn`、`card`），即使样式完全不同，也会导致以下问题：

1. **命名冲突**：在已使用 daisyUI 的项目中同时引入 Neo-Brutal UI 会产生类名冲突。
2. **生态混淆**：用户会误以为 Neo-Brutal UI 是 daisyUI 的插件或皮肤，而非独立项目。
3. **品牌独立性**：项目需要建立自己独立的类名体系和品牌认知。

因此，我们需要做出一个架构级决策：Neo-Brutal UI 是独立实现，还是基于 daisyUI 的二次开发。

## 决策（Decision）

**Neo-Brutal UI 采用完全独立的实现方案**。具体包括：

1. **不直接复用 daisyUI 的任何类名**，所有类名以 `nb-` 为前缀（如 `nb-btn`、`nb-card`）。
2. **不将自身定位为 daisyUI 的主题或皮肤**，而是以独立 npm 包 `neo-brutal-ui` 发布。
3. **借鉴但不依赖**：我们借鉴 daisyUI 的组件分类哲学和 API 设计思想（如语义化组件类 + 变体修饰符的组合模式），但所有实现从零编写，拥有完全独立的 DOM 结构、CSS 和主题系统。
4. **主题系统独立**：不使用 daisyUI 的主题配置文件或主题扩展机制，而是自建基于 `data-theme` 和 CSS 自定义属性的主题体系。

## 替代方案（Alternatives）

### 替代方案 1：Fork daisyUI 并修改样式

- **描述**：直接 Fork daisyUI 的源码仓库，将其默认样式替换为新粗野风格，保留原有类名和组件结构。
- **未采纳原因**：
  - 类名冲突问题无法解决（`btn` 与 daisyUI 的 `btn` 重叠）。
  - 无法建立独立品牌认知。
  - daisyUI 的 DOM 结构针对其默认视觉设计优化，新粗野风格需要不同的 DOM 结构（如硬阴影边框需要额外的 wrapper 或伪元素）。
  - 需要长期同步 upstream 的更新，维护成本极高。

### 替代方案 2：作为 daisyUI 的官方或第三方插件/主题

- **描述**：将 Neo-Brutal UI 开发为 daisyUI 的主题包，通过 daisyUI 的主题配置机制加载。
- **未采纳原因**：
  - 新粗野风格的 DOM 结构需求（如偏移阴影、双层边框）超出 daisyUI 主题系统的能力范围。
  - 主题机制无法提供独立的 JavaScript 交互层。
  - 项目愿景是成为与 daisyUI 并列的独立组件库，而非其附属品。
  - 长期受制于 daisyUI 的版本节奏和架构演进。

### 替代方案 3：完全独立的类名但不借鉴 daisyUI 的 API 设计

- **描述**：不仅类名独立，连组件分类和 API 设计模式也重新发明。
- **未采纳原因**：
  - daisyUI 的组件分类和 API 设计已被大量开发者验证和接受，重新发明一套完全不同的模式会增加学习成本。
  - 借鉴成熟的 API 设计可以降低用户的迁移成本（从 daisyUI 切换到 Neo-Brutal UI 时，只需添加 `nb-` 前缀和适应变体名称）。
  - 无充分理由拒绝已被证明成功的设计模式。

## 影响（Consequences）

### 正面影响

- **完全自主控制**：类名、DOM 结构、主题系统、交互逻辑全部自主可控，不受外部项目架构限制。
- **无命名冲突**：`nb-` 前缀确保与 daisyUI 及其他组件库共存时不会产生类名冲突。
- **独立品牌**：项目拥有清晰的品牌边界和独立生态位。
- **架构灵活**：未来演进（如支持 Web Components、添加新的主题）完全由项目自身决定。
- **开发者心智模型清晰**：用户明确知道这是"Neo-Brutal UI"，不是"daisyUI 的某个主题"。

### 负面影响 / 风险

- **无法复用 daisyUI 生态**：不能直接使用 daisyUI 的第三方主题、插件或社区资源。
- **从零建立用户基础**：需要独立推广和教育市场，不能借助 daisyUI 的用户惯性。
- **组件实现工作量大**：每个组件的 DOM 结构、CSS 和 JS 都需要从零编写，不能参考 daisyUI 的实现代码（只能借鉴设计思想）。
- **潜在的分裂风险**：如果未来 daisyUI 推出类似的粗野风格主题，可能形成竞争。

### 技术债务 / 后续工作

- 需要建立完整的组件 API 文档，证明独立设计的合理性。
- 需要制定与 daisyUI 的 API 映射关系文档（帮助用户迁移），但明确声明这不代表兼容性承诺。
- 持续关注 daisyUI 的 API 演进，确保 Neo-Brutal UI 的 API 设计不会与其偏离过远，导致用户学习成本过高。
